# Migration from 5.3.16 to 5.3.17

## Invariant

Migration is additive. Existing bytes remain immutable. No legacy record becomes native 5.3.17 authority merely because a field name or digest string was changed.

## Phases

1. Quiesce authority writes while allowing bounded reads.
2. Install the 5.3.17 descriptor, schema registry, relation registry, and crypto suite registry.
3. Run provider self-tests and load protected signing and KEM keys.
4. Create new variable-length cryptographic columns and normalized meta-object edge tables.
5. Import legacy records into a read-only replay namespace with their original bytes and provenance.
6. Select records eligible for migration under governance policy.
7. Canonicalize each selected semantic body under 5.3.17 and compute its new semantic content ID.
8. Construct a new envelope with explicit observer, chronology, dependencies, corpus, and policy.
9. Generate a `LegacyMappingWitness/v1` binding old opaque identity, old bytes, new semantic ID, new envelope ID, migration policy, and execution witness.
10. Produce a native ML-DSA-87 attestation using an active 5.3.17 key. Never copy or translate old signature bytes.
11. Rebuild audit checkpoints and anchors in a new epoch. Preserve the legacy root as an opaque migration input.
12. Shadow-read both namespaces, compare behavior, and emit non-collapse differences.
13. Enable 5.3.17 writes only after all P0 checks and external activation policy succeed.

## Rollback

A software rollback may disable new writes but cannot erase or reinterpret 5.3.17 records. Software that cannot verify a critical 5.3.17 feature must enter read-only compatibility mode.
